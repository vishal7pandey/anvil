# Defect fix (RTEMS)

## When to use
A ticket describes wrong behaviour (crash, wrong return value, leak, hang) in an RTEMS repository.

## Ground rules
- Never claim a result you did not see in command output. Quote the output.
- Do not search the internet or other branches for the fix. Work from the code, the ticket and
  the history of the branch you are on.
- Smallest correct change. No drive-by refactoring, no reformatting of untouched lines.
- Never weaken, skip or delete an existing test. Never touch `.github/`.

## Steps (keep them as your write_todos plan)

1. **Understand the report.** Restate the expected vs. actual behaviour in one line each.
   Identify the API entry point named in the ticket (e.g. `pthread_mutex_init`).
2. **Locate the code.** `grep -rn "<function>" cpukit/ --include=*.c` and read the implementation
   top to bottom, including every early-return/error path. Read `git log -p --follow <file>`
   for recent changes. Delegate long traces to the `investigator` subagent.
3. **Reproduce with a test first.** Find the existing test program for that API
   (`grep -rln "<function>" testsuites/`; POSIX APIs live in `testsuites/psxtests/psxNN/`).
   Extend that test (prefer extending over adding a new test program: new programs need
   build-spec entries under `spec/build/testsuites/`). The new check must fail on the
   unfixed code for the reported reason.
4. **Build and run the failing test** (via the `builder` subagent or directly):
   ```sh
   cd /workspace/rtems
   cat > config.ini <<'EOF'
   [sparc/erc32]
   BUILD_SAMPLES = False
   BUILD_PSXTESTS = True
   EOF
   ./waf configure --prefix="$RTEMS_PREFIX"
   ./waf -j"$(nproc)"
   rtems-test --rtems-bsp=erc32-sis build/sparc/erc32/testsuites/psxtests/psx05.exe
   ```
   Use the test suite that matches the API (`BUILD_SPTESTS` for Classic API in `sptests`,
   `BUILD_FSTESTS` for file systems, ...). Record the failing output: it is evidence.
5. **Root cause.** State it precisely: file, function, line, and *why* the code is wrong
   (e.g. "object state written before validation; the EINVAL path returns with a half-initialised
   object"). If you are not sure, keep investigating; do not guess-fix.
6. **Fix.** Make the change. Match RTEMS style: 2-space indentation, a space inside the
   parentheses of calls and conditions `if ( x == NULL ) {`, comments in `/* */`.
7. **Verify.** Rebuild; run the new check (must pass) and the whole suite for that area:
   `rtems-test --rtems-bsp=erc32-sis build/sparc/erc32/testsuites/psxtests/` (must not regress).
   Paste the pass/fail summary.
8. **Review.** Ask the `reviewer` subagent to review `git diff`. Address findings.
9. **Pre-commit.** If `.pre-commit-config.yaml` exists: `pre-commit run --files <changed files>`
   (the files in `git status --porcelain`). Never `--all-files`: on RTEMS it runs for 30 minutes
   and the sandbox refuses it. Fix what it reports (formatting of changed lines only).
10. **Commit** on your `anvil/...` branch:
    ```
    <JIRA-KEY>: <component>: <what was fixed>

    Root cause: ...
    Fix: ...
    Tests: <test> extended; <suite> passed on erc32/SIS (<N> tests).
    ```
    Write the message to a file and use `git commit -F <file>`: `\n` inside `git commit -m "..."`
    is not a newline, it ends up as literal text on one line.
11. **Push and PR**, in this order: commit, then `git_push(branch=...)`, then `github_open_pr`
    with the PR body below (it fails until the branch is pushed). The repo, the PR's base branch and
    the ticket are fixed by the run; you don't pass them. Then `github_checks(pr)`; if CI fails,
    read the log, fix, commit, push (max 3 rounds), else `handoff`. State `none` means no CI ran:
    that is not a pass. The runtime checks the PR and its CI itself before the run counts as done.
12. **Evidence.** `jira_comment` with root cause, fix, tests, PR link and CI status; label the
    ticket `anvil-in-review` with `jira_set_labels(add=[...])`.

## PR body template
```
## Root cause
<precise explanation with file:line>

## Fix
<what changed and why it is sufficient>

## Tests
- Reproduced: <test> failed before the fix: <quoted output>
- After the fix: <test> passes; <suite> on sparc/erc32 SIS: <passed>/<total>

## Risk
<what else could be affected; why it is not>

Generated by Anvil run <run_id>.
```

## When to stop and hand off
Call `handoff` when: the same build or test failure persists after three different attempts;
the fix needs hardware or a BSP you cannot run; the ticket is ambiguous about expected
behaviour; or CI is still red after three rounds.
